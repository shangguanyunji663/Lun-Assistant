# 数字可信度定稿：四条指标的真实水位与简历写法

> 日期：2026-10-05
> 前置：`docs/DATA_INTEGRITY_AUDIT.md`（证据链审计与 P0 修复）
> 本文档回答一件事：**这四类数字现在到底能怎么写，才经得起面试官追问。**

---

## 〇、总原则

面试官看到 `100%` / `20/20` / `16/16` / `0.212` 时，脑子里问的**不是「多好」**，而是：

> 「这个数怎么来的？坏的时候长什么样？」

答不上后半句，前面的数就全废。**能说出 miss 在哪的人，别人才信他的 hit。**

三个「满分形数字」的病根相同：**没有分母、没有难度、没有失败面**。
修法不是把数字改小，而是**换成有刻度、有归因、有边界的写法**。

## 一、意图分类

### 真实水位（两套口径，都有产物）

| 集合 | 条数 | 准确率 | 分层 | 产物 |
| :--- | :--- | :--- | :--- | :--- |
| `intent.jsonl`（含 L1 触发词） | 50 | **92.0%** | rule 23 / vector 26 / llm 1 | `evals/results_latest.json` |
| `intent_holdout.jsonl`（**零原型句重叠**，全部避开 L1 触发字） | 92 | **76.1%** | rule 1 / vector 42 / llm 49 | `evals/results_intent_holdout.json` |

**分层错误率（hold-out，这才是关键）**：

```
rule    0.0%  ( 0/ 1)
vector 38.1%  (16/42)   ← 向量层是 LLM 层错误率的 3 倍
llm    12.2%  ( 6/49)
```

### 🔴 结构缺陷：L2 的 0.62 阈值不是一个有效的置信度门

```
向量层 correct 置信度: n=26  0.622 ~ 0.909  平均 0.672
向量层 wrong   置信度: n=16  0.622 ~ 0.709  平均 0.655   ← 区间完全重叠
```

正确与错误的平均置信度只差 **0.017**，**余弦相似度在 0.62 附近无法区分对错**。
42 条向量层判定全部落在 0.62~0.71 → 全部被放行 → **LLM 兜底层本轮一次都没被启用**。

**可执行结论**：不该微调阈值，而应把 L2 判定**改送 LLM 复核**，或改用真正有区分度的信号
（top-1 与 top-2 的 margin、长度归一化）。阈值提到 0.70 即可转交 14/16 的当前错误。

### 另外一个规则层缺陷

`writing` 规则第一分支是**裸的 `写`**（`services/classifier/intent.py:32`），导致：

```
今天天气不错适合写东西     → writing（conf 0.95）
陪我聊聊我实在写不下去了   → writing（conf 0.95）
```

规则层以 0.95 置信度判错，而 **100% 的指标永远看不见它**。

### ✅ 简历写法

```
三层意图预分类（规则→向量→LLM）：规则层独立覆盖 23/50（46%）、零 token 开销。
  在含关键词的 50 条集上 92%；另建 92 条零重叠 hold-out 集（刻意全部避开 L1 触发词，
  用于度量"规则层覆盖不到的 59% 长尾流量"）盲测得 76.1%。
  分层错误率显示：rule 0%、llm 12.2%、vector 38.1% —— 定位到 L2 的 0.62 阈值失效
  （correct 均值 0.672 vs wrong 0.655，区间重叠，无法区分对错），
  故向量层实际在阻止更准的 LLM 介入；改进方向是 L2 转 LLM 复核而非调阈值。
```

```
三阶段 RAG（改写→多路 RRF 融合→交叉精排）。

  简单集 20/20（字面重合 67.5%，其中 4 条 ≥85%）
```

**要点**：`100%` 不再单独出现，而是「最易档」的刻度值，并紧跟难度说明。

## 三、上下文压缩率

### 🔴 合成 fixture 掩盖了两个生产缺陷（已定位并修复）

| 口径 | 修复前 | 修复后 | 判定 |
| :--- | :--- | :--- | :--- |
| 合成填充文本（harness 口径，`"背景填充"*120`） | 0.212 | 0.213 | ✅（**对该 bug 不敏感**） |
| 真实语料 · `keep_recent=0`（**生产路径**） | **1.000** | **0.035** | ❌ → ✅ |
| 真实语料 · `keep_recent=4`（历史发布口径） | 0.767 | 0.191 | ❌ → ✅ |
| 真实语料 · `keep_recent=None`（375） | 1.000 | 1.000 | 窗口大于内容 → 本轮不压缩（正确） |

产物：`evals/results_compression_real.json`

### 根因 1：高价值判定用裸子串匹配

```python
# services/memory/compressor.py:18（修复前）
_HIGH_VALUE_MARKERS = ("纠正", "不对", "改成", "记住", "重要", "必须", "要求")
```

「要求 / 重要 / 必须」是中文论文正文的高频词。实测归因：

```
高价值消息 11/24 条、7903 字  →  占全文 66.2%（强制保留、永不压缩）
  其中误判 8 条、7775 字        ←  全是 assistant 正文
  真实用户纠正只有 3 条、284 字
标记命中：要求×8  重要×4  必须×4  记住×2
```

即：**3 条真实纠正（284 字）连带把 7775 字正文永久保留**。

*修复*：判定改三档 —— ① 非 `user` 角色一律可压；② 显式纠正词（纠正/不对/改成/改为）
命中即保留；③ 泛化词（重要/必须/要求/记住）须与持久化动作（别改/务必/以后都…）同现。
**修复后：误判 0 条，高价值占比 66.2% → 1.1%。**

### 根因 2：`keep_recent` 用真值判断，生产压缩链路从未压缩

```python
keep_recent = keep_recent or max(6, cfg_keep)   # 传 0 → 被静默替换成 375
if keep_recent and len(rest) > keep_recent:     # 0 为 falsy → 走"全部保留"
```

生产路径 `compress_window_if_needed()` 传 **`keep_recent=0`**（语义："被逐出消息整体压缩"），
但 `0` 在两处都被当成"未指定" → 实测 **ratio=1.000、摘要 0 字**，压缩从未发生。

*修复*：改用 `is None` 判断 + 显式分支 `keep_recent == 0 → 整段压缩`；
并补 `len(rest) > keep_recent` 条件（窗口大于内容时原样保留，而非把短会话压成摘要）。

### 为什么合成 fixture 发现不了

它用「背景填充」重复文本，**一个高价值标记词都不含**（绕过根因 1）；
又走 `keep_recent=4`（绕过根因 2）。**所以它两次都报 PASS（0.212 / 0.213）。**

### ⚠️ 修复后新暴露的取舍（未解决）

生产路径 0.035 意味着 **24 条消息里 21 条被压成一份 282 字摘要**，信息损耗显著。
压缩率达标 ≠ 摘要保真；真正的验收应是"压缩后能否复述任务目标与已完成结论"，
而这一维度目前**没有度量**。这比 0.035 本身更值得说。

### ✅ 简历写法

```
四层记忆分级留存 + 真 LLM 摘要压缩。
  压缩率在合成 fixture 上 0.212，换真实语料复测发现生产路径实际为 1.000
  （即从未压缩），定位两个根因：
  ① 高价值标记全篇子串匹配，把中文正文里的「要求/重要/必须」误判为用户纠正，
     致 66.2% 字数被强制保留；
  ② keep_recent 用真值判断，生产传入的 0 被替换成默认值，截断分支永不生效。
  修复后生产路径 0.035、keep_recent=4 口径 0.191，并补 6 个离线用例锁定语义。
```

**这条的价值**：它证明你会**怀疑自己的测试**，能定位到根因而非调参，且区分了"压缩率达标"与"摘要保真"。

## 四、回归 16/16

`16/16` 本身没问题（16 项断言全过，且全部可失败）。问题是**「全过」是空信息**。

### ✅ 简历写法

```
7 场景 16 项断言，全部为可失败的真断言（相邻窗口召回 [1,3]、拒答回退、
  图 10 节点装配、产物骨架渲染等）。
  其中 4 项在审计中被发现是「无条件 True / import 即 PASS / 常量自比」，
  已重写并做变异验证（改坏被测逻辑 → 断言变红 → 还原）。
```

**「我知道什么是假测试」比「我全过了」有力得多。**
