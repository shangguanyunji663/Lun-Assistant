## 〇、先给结论

这个项目的**后端工程含量是真实的**——三阶段 RAG、七步治理栈、LangGraph 编排、
三级 Checkpointer、四层记忆，都是真实现、真测试。问题不在引擎，在**证据层**：

前端展示的那几个数字（100% / 16/16 / 100% / 93）**不是从当前代码里量出来的**，
而是 2026-09-03 在旧数据集上跑出来的残值，被抄进了 8 个 HTML 页面。
数据集后来扩容了，评测没重跑，数字没更新。

对简历来说这恰恰是最危险的位置：面试官只要打开 `evals/results_latest.json`，
看到 `cases: 8, recall: 0.875`，而页面上写着 100% / 20 条——**项目立刻从"工程扎实"
变成"数据注水"**，前面所有真实的工程投入都会被这一个反差推翻。

## 一、核心问题：数字链条断了

### 1.1 落地页 24 处硬编码（6 页 × 4 个数字）

| 位置 | 内容 |
| --- | --- |
| `frontend/index.html:336,341,346,351` | 100% / 16/16 / 100% / 93项 |
| `landing-b.html:472,478,484,490` | 同上 |
| `landing-c.html:433,438,443,448` | 同上 |
| `landing-d.html:358,363,368,373` | 同上 |
| `landing-e.html:417,422,427,432` | 同上 |
| `landing-f.html:414,419,424,429` | 同上 |

（`how-it-works.html` / `dossier.html` 无此读数区，不受影响。）

这 6 个页面**互相复制同一组数字**，既非接口拉取，也无数据来源标注。
`data-count` 只是让数字滚动动画更好看，不参与任何真实取值。

### 1.2 意图分类「100% · 50 条集」——测的是 22 条

| 来源 | 值 |
| --- | --- |
| 落地页宣称 | 50 条集，100% |
| `evals/results_latest.json` | `cases: 22`，`accuracy: 1.0` |
| `evals/datasets/intent.jsonl`（当前） | **50 条** |
| `evals/datasets/intent.jsonl`（扩容前 `4ae3ddd`） | **22 条** |

时序证据：commit `30b4fe1`（2026-09-04）把数据集从 22 → 50 条，
但 `results_latest.json` 仍停在 22 条那一版，**从未重跑**。

即：**100% 是在 22 条上测的，50 条版本的准确率没人知道。**

补充：50 条里正则层（L1）可独立命中 23 条且全对；其余 27 条要走向量层/LLM。

### 1.3 Recall@5「100%」——三个来源互相打架

| 来源 | 值 |
| --- | --- |
| 落地页 | 100% |
| `evals/results_latest.json` | `cases: 8`，`recall: 0.875`，`avg_ms: 75308` |
| `docs/EVALUATION_REPORT.md` | 100%（20/20），平均 75.3s/条 |
| `evals/datasets/retrieval.jsonl`（当前） | **20 条** |
| 同上（扩容前 `4ae3ddd`） | **8 条** |

`results_latest.json` 的 8 条与扩容前数据集条数**完全吻合**，
说明它同样是旧产物。而 `EVALUATION_REPORT` 写的「20/20 @ 75.3s/条」
与 `results_latest` 的「8 条 @ 75.3s」**算术上无法同时成立**
（8 条均值 75.3s → 总耗时约 10 分钟；20 条均值 75.3s → 约 25 分钟）。
两个数字来自不同批次，被拼在了一起。

**结论：20 条版本的 Recall@5 没有任何可复现产物支撑。**

### 1.4 回归「16/16」——其中 2 项是硬编码 `True`

`evals/regression.py` 原文：

```python
# 第 164 行
_record("S3", "相邻窗口查询语法", True, f"sibling call ok (rows={len(sib)}, DB依赖登记为S1)")
#                                  ^^^^ 无条件 PASS，实际 rows=0

# 第 174 行
_record("S4", "改写策略回退", True, "LLM 拒答路径逻辑已内置（服务依赖场景见冒烟）")
#                              ^^^^ 无条件 PASS，detail 自承"已内置"，未执行任何断言
```

16 项里逐条定性：

| 项 | 性质 |
| --- | --- |
| S1 入库与MD5去重 / 扫描件拒绝 / 分块落库 | ✅ 真行为断言 |
| S2 跨项目隔离 | ⚠️ 真断言但弱（期望 0 命中、实际 0） |
| S3 RRF融合 | ✅ 真断言 |
| S3 相邻窗口查询语法 | ❌ **硬编码 True，rows=0** |
| S4 规则改写 | ✅ 真断言 |
| S4 改写策略回退 | ❌ **硬编码 True** |
| S5 复杂任务识别 ×3 | ⚠️ 真断言，但用例与规则同源（见 1.6） |
| S5 Planner 节点装配 | ❌ 仅 `import` 成功即 PASS |
| S6 产物模板覆盖 | ❌ 校验常量元组等于字面量（恒真） |
| S6 参数校验 | ✅ 真断言 |
| S7 工具与配置一致 / RBAC放行 | ⚠️ 配置一致性检查，非行为验证 |

**实际有效行为断言约 10/16。** 且「16/16」是子项计数，页面文案却暗示
「S1–S7 七大场景全通」——两件事被混为一谈。

### 1.5 压缩率 0.214——测在合成重复文本上

`evals/harness.py:86` 的 fixture：

```python
msgs.append({"role": "user", "content": f"第{i}轮提问：请围绕论文选题给我建议。" + "背景填充" * filler})
```

`filler=120`，即每轮塞 120 遍「背景填充」。**高度重复的合成文本，
任何压缩算法都能拿到漂亮数字。** 这不测真实对话的压缩能力，
9920 → 2121 的 0.214 因此没有说服力。

（注：压缩器本身是真实现——分级留存 + 冗余去重 + 窗口截断 + **真 LLM 摘要**，
`services/memory/compressor.py:102`。坏的是输入，不是算法。）

### 1.6 意图测试集与 L2 原型句同源（轻度泄漏）

L2 向量层用原型句做余弦比对（`intent.py:47-55`），
而测试集里多条是原型句的近义改写：

| 测试集 | 原型句 |
| --- | --- |
| 「你能做什么」 | 「你能做什么」（**逐字相同**） |
| 「谢谢你的帮助」 | 「谢谢帮助」 |
| 「帮我找几篇关于大语言模型的文献」 | 「找几篇核心期刊论文」 |

即「用原型句当参考答案，再用它的改写当考题」。全库 50 条中 1 条逐字相同，
多条近义——不足以否定结论，但足以让 100% 打折。

### 1.7 命名夸大

| 工具 | 实际实现 | 问题 |
| --- | --- | --- |
| `check_plagiarism` | 字符 bigram Jaccard，比对 81 篇本地语料 | 不是查重，是「本地语料相似度自查」 |
| `detect_ai_text` | LLM 自判 + 句长方差/高频词启发式 | AI 检测本身不可靠，LLM 自判尤甚 |

代码是诚实的（docstring 写了「估算」「痕迹」），但**工具名和落地页文案在宣称
它们做不到的事**。

## 二、真实且值得写进简历的部分

不要因为上面的问题否定整个项目。以下经查证**确为真实现**：

| 能力 | 证据 |
| --- | --- |
| **三阶段 RAG** | 81 篇真实语料（14–39KB/篇，内容为真实学术文本）；bge-m3 稠密 + BM25(jieba) 稀疏 + 相邻窗口 → RRF 融合 → bge-reranker-base 交叉编码器精排。`services/rag/` |
| **七步治理栈** | RBAC(YAML) → Redis 滑动窗口限流(Lua 原子) → 三态熔断(Lua 原子) → 分布式锁 → 三级容错(重试/降级/人机) → 审计落库 → 行为观测沉淀 Skill。14 个工具统一纳管。`services/governance/` |
| **治理的可靠性有测试锁定** | `tests/test_tool_registry_call.py` 13 个用例，含「Redis 故障时工具链路 fail-closed + 审计必落库 + 原始异常不被替换」三项契约 |
| **LangGraph 编排** | supervisor + 6 专项 Agent + Plan-Execute-Replan planner；`interrupt`/`resume` 人机介入 + Redis→PG→内存 三级 Checkpointer |
| **四层记忆 + 压缩** | L1 短期(Redis) / L2 结构化 / L3 长期向量 / L4 偏好；压缩走真 LLM 摘要 |
| **93 个离线用例真实通过** | `pytest tests/ -q` → 93 passed；`ruff check .` → All checks passed |
| **A/B 报告诚实记录负结果** | `evals/AB_REPORT.md` 明确写了「改写不提升召回」「改写纯开销 2.2s → 61s」——这是**加分项**，多数作品集不敢写失败 |

**这份清单本身就很硬。** 它支撑的是「Agent 应用开发」岗位真正看的东西：
工具治理、编排、可观测、容错——不是准确率数字。

## 五、修复方案

### P0 · 必做（否则不要把这个数字放上简历）

1. **重跑评测，让产物与数据集一致**
   起 PG + Ollama 后执行 `python evals/harness.py`，用当前 50 / 20 条数据集
   重新生成 `results_latest.json`。跑出多少写多少——**哪怕掉到 88% 也比 100% 可信**。

2. **落地页数字改为可追溯**
   把 24 处硬编码换成「数字 + 口径 + 产物路径」三件套，例如：

   > Recall@5 **87.5%** · 20 条检索集 · 见 `evals/results_latest.json`

   宁可暴露真实数字，也不要 100%。**一个带口径的 88% 比一个裸的 100% 强得多。**

3. **删掉 `regression.py` 两处硬编码 `True`**
   第 164 行改成真断言（断言 `rows >= 0` 无意义，应改为注入邻块数据后断言能取回）；
   第 174 行要么实现拒答回退的真测试，要么直接删除并改称「15 项」。

### P1 · 建议

4. 压缩 fixture 换成真实多轮对话（可用 `demo.js` 的会话文本或语料片段拼接），
   重测压缩率。
5. 意图测试集去泄漏：删掉与原型句逐字/近义重复的条目，补充口语化长尾样本。
6. 工具改名与文案降级：`check_plagiarism` → 「本地语料相似度自查」，
   `detect_ai_text` 明确标注「LLM 自判，仅作提示，不作判定依据」。
7. `EVALUATION_REPORT` 里「20/20 @ 75.3s」按重跑结果订正，消除与产物的算术冲突。

### P2 · 锦上添花

8. 起 PG + Ollama，录一段 3 分钟真实演示（含时间线、interrupt 确认、trace 回放）。
   **一段能跑的录屏 > 十个 100%。**
9. README 增加「如何复现这些数字」一节，列出命令与预期产物。

## 六、简历上该怎么改口径

| ❌ 现在这样写 | ✅ 建议改成这样写 |
| --- | --- |
| 意图分类 Top-1 100% | 意图分类三层预分类：正则层覆盖 46%（23/50）零开销，其余下沉向量/LLM |
| RAG Recall@5 100% | 三阶段 RAG（改写→多路 RRF 融合→交叉精排）；A/B 实测：改写不提升召回，但 MRR +0.17 |
| 回归 16/16 全通 | 7 大场景回归脚本化，16 项断言覆盖入库/隔离/融合/改写/路由/产物/治理 |
| 压缩率 0.214 | 四层记忆分级留存 + LLM 摘要压缩，压缩率 0.21（目标 ≤0.3） |
| 查重降重 / AI 检测 | 本地语料相似度自查 / AI 痕迹提示（明确标注算法边界） |

**核心原则：写机制、写边界、写失败教训，不要写满分。**
`AB_REPORT` 里那句「改写不提升召回，纯开销 2.2s→61s」比任何 100% 都更像
一个真正做过工程的人说的话。
