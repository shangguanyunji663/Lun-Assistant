# 密码学：对称与非对称加密、哈希、数字签名与PKI
# 收录于 计算机检索增强语料库
一、引言
　　密码学（Cryptography）是研究信息在传输与存储中保密、完整与防篡改的技术与数学分支，是网络安全、数据安全、身份认证与数字支付的基石。从登录口令的加盐哈希，到 HTTPS 的 TLS 握手、电子政务的数字签名、区块链的哈希链，密码学无处不在。理解密码学并不需要成为数学家，但必须把握其核心概念、算法类别、安全边界与工程使用方式，才能正确选型并避免"用错算法"这一最常见的错误。
　　本文将从密码学的目标讲起，依次介绍对称加密、非对称加密、哈希函数、数字签名、证书与公钥基础设施（PKI）、TLS 握手，以及量子时代的密码学展望，并结合检索增强语料的知识组织说明落地要点。
二、密码学的基本目标与密码体制
　　密码学要解决四类问题，前三个正对应前面所说的 CIA 三角：机密性（只有持有密钥者能读取）、完整性（数据未被篡改）、真实性/认证（消息确由声明者发出且来源可信）、以及不可抵赖性（发送者无法否认已发出的消息）。密码体制通常分为对称与非对称两大类，二者在密钥管理、性能与用途上差异显著。
　　现代密码学遵循"柯克霍夫斯原则（Kerckhoffs's principle）"：算法的安全性应完全建立在密钥的保密性上，而非算法的保密。因此算法是公开的、经得起公开检验的标准（如 AES、RSA），用户只需保护密钥。这一原则也提醒我们：永远不要自研加密算法，应使用经过严格审查的成熟算法与库实现。
　　对称加密用同一个密钥加解密，速度快、适合大数据量；非对称加密用一对"公钥+私钥"，速度慢、适合密钥交换与数字签名。哈希既非加密也非解密，而是一个方向的压缩映射，用于完整性校验与口令存储。实际系统中，通常用非对称加密协商一个临时的会话密钥，再用对称加密保护正文，这就是混合加密（Hybrid Cryptography）的思路，TLS 正是如此。
　　这里需要弄清一个常见误区：加密（Encryption）与编码（Encoding）不是一回事。编码（如 Base64、URL 编码、UTF-8）只是把数据变换为另一种表示形式，目的是可传输/可打印，任何人都能解码还原，并不保护机密性；加密则依赖密钥、未经授权者无法还原明文。另外，"哈希（Hash）"不等于"加密"，哈希不可逆、无密钥、用于校验与指纹；"压缩（Compression）"也不等于加密，压缩是可逆且无密钥保护的。混淆这些概念是新手常犯的错误，也会导致把敏感数据直接 Base64 就当作"加密"的危险做法，务必警惕。
三、对称加密：AES 与 DES
　　对称加密（Symmetric Encryption）是加解密使用相同密钥的密码体制，可分为分组密码（Block Cipher，按固定数据块处理）与流密码（Stream Cipher，按字节/位连续处理）。
　　1. DES（数据加密标准）。曾是美国国家标准，使用 56 位密钥，因密钥过短早已被破解，如今仅具历史意义，不应在实际系统中使用。为增强安全性出现的 3DES（三重 DES，用不同密钥加密-解密-加密三次）虽延长了有效密钥长度，但因性能差且遗留安全隐患，也逐步被更现代的算法取代。
　　2. AES（高级加密标准，Advanced Encryption Standard）。当前对称加密的事实标准，支持 128/192/256 位密钥，分组 128 位，被全球广泛采用并内置了硬件加速（AES-NI）。Rijndael 算法被选为 AES，其安全性经过了充分检验。推荐使用 AES-256-GCM 这类认证加密模式。
　　3. 分组密码的操作模式。AES 等分组密码需要配合操作模式（Mode）使用。常用模式包括 ECB（电码本模式，固定明文块→固定密文块，存在模式泄露，不安全）、CBC（密码块链接模式，前一块密文参与当前块加密，但需要合适的初始化向量 IV 且无完整性保护）、CTR（计数器模式）/GCM（伽罗瓦计数器模式，同时提供机密性与完整性认证的认证加密 AEAD）。工程上强烈推荐 GCM/ChaCha20-Poly1305 等 AEAD 模式，避免"加密了但没做完整性保护"的漏洞。IV/Nonce 绝不能重复使用，否则会直接泄露密钥与明文。
　　4. 流密码。如 RC4（已废弃）、Salsa20/ChaCha20（现代性能优秀的流密码，常用在 TLS 与移动端）。它们适合实时或资源受限场景。
　　5. 密钥派生与口令派生的区别。当需要从主密钥或口令派生出适合 AES 的固定长度密钥时，要区分两类算法：一是基于口令的密钥派生函数（如 PBKDF2、scrypt、Argon2），设计目标是"慢、占内存、抗暴力/抗专用硬件"，用于把人类口令安全地变成密钥；二是标准的密钥派生（KDF），如 HKDF、HMAC 类，用于把随机主密钥扩展/分离出多个用途分散的密钥（加解密、认证、导出），设计目标是高效且可打散关联；而口令派生函数因效率低只用于口令场景，不做日常密钥分离。工程上，掌握"口令走慢哈希、密钥走 KDF、nonce 不重用、完整性交给 AEAD"这组口诀，能规避绝大多数对称加密的使用错误。
五、非对称加密：RSA 与 ECC
　　非对称加密（公钥密码，Asymmetric / Public-Key Cryptography）使用一对数学关联的密钥：公钥可公开分发，私钥必须保密。用公钥加密，则只有私钥能解密（用于机密性）；用私钥签名，则任何人可用公钥验证（用于数字签名与认证）。其安全性建立在数学难题之上，如大整数分解与离散对数、椭圆曲线难题。
　　1. RSA。基于大整数分解难题，密钥由两个大素数生成，广泛用于密钥交换与数字签名（如 RSA-OAEP 加密、RSA-PSS 签名）。安全强度随密钥长度增长：2048 位被视为当前最低可用，4096 位更稳妥，但随着算力提升与量子威胁，RSA 正逐渐向 ECC 迁移。
　　2. ECC（椭圆曲线密码，Elliptic Curve Cryptography）。基于椭圆曲线离散对数难题，在同等安全强度下密钥长度远小于 RSA（如 256 位 ECC 大致等同 3072 位 RSA），速度与带宽更优，因此成为现代首选。常见曲线如 P-256、secp256k1（比特币使用）、X25519（Curve25519，用于密钥交换）。
　　3. 密钥交换协议。Diffie-Hellman（DH）协议让双方在不安全的公共信道上协商出共享的对称密钥；其椭圆曲线版本 ECDH 更高效。市面上流行的 X25519 即 ECDH 的实现。注意：纯 DH 无法防中间人攻击，需配合认证（证书/签名）才能建立可信信道（这正是 TLS 所做）。
　　4. 重要原则。私钥必须妥善保管并使用硬件安全模块/密钥库（如 KMS/HSM）保护；公钥加密扩展性差（长消息不适合用 RSA/ECC 直接加密），所以公钥通常用于加密"会话密钥"或用于签名。切忌直接把长明文用非对称算法加密。实际上，公钥加密最典型的"封套（Envelope）"用法是：用对称密钥加密正文、再用接收方公钥加密该对称密钥，二者一并交付，既获得非对称的分发便利，又保留对称加密对大数据量的高效性。此外还要警觉填充（Padding）的重要性——如 RSA 需使用 OAEP 而非教科书的裸 RSA，否则易受选择密文攻击（CCA）；ECC 协议实现在实施时若常数时间处理不当还有侧信道与坏点攻击的风险，因此务必使用经过审计的成熟库而非自行拼装原语。
五、哈希函数与口令安全
　　哈希（Hash）函数是确定性单向映射，把任意长度输入压缩为固定长度输出（摘要，Digest），具有雪崩效应（输入微小变化输出巨大变化）、不可逆、抗碰撞等特性，用于数据完整性校验、口令存储、指纹/寻址与数字签名的基础。
　　1. 常见算法。MD5 已不安全（可碰撞、可快速破解），SHA-1 也已被证明可碰撞、仅剩少数旧场景；现代推荐 SHA-256、SHA-3（Keccak）等 SHA-2 家族。口令哈希不能直接用普通哈希，而应使用慢速+加盐（Salt，随机串混合进每个口令）的专门算法：bcrypt、scrypt、PBKDF2、Argon2（当前推荐，内存困难型，抗专用硬件攻击）。加盐保证相同口令得到不同哈希，拖库后难以用彩虹表还原。
　　2. 消息认证码（MAC）与 HMAC。为验证"消息未被篡改 + 来源可信"，可使用密钥化的哈希——HMAC（哈希关键的消息认证码，如 HMAC-SHA256）。它要求双方共享密钥，用于 API 鉴权、Cookie 签名、Webhook 校验等。注意区别：哈希做完整性但无密钥保护；MAC/HMAC 提供完整性与真实性。
　　3. 使用要点。哈希用于比对时使用恒定时间比较（如 message/hmac.compare_digest）防止时序侧信道；对敏感值（口令、Token）绝不存明文，也应避免快速哈希。
六、数字签名与证书、PKI
　　数字签名（Digital Signature）是"私钥签名、公钥验证"应用于消息的过程，提供认证、完整性与不可抵赖性。典型流程：对消息哈希后，用签名者私钥对摘要加密签名，验证者用签名者公钥解密并与消息哈希比对。常用方案有 RSA-PSS、基于 ECDSA/EdDSA（如 Ed25519）的签名。
　　这里出现"信任链"问题：验证者如何确信"这个公钥确实属于声称的那个人"？答案就是证书与公钥基础设施（PKI, Public Key Infrastructure）。
　　1. 数字证书（Digital Certificate）。由证书颁发机构（CA, Certificate Authority）签发，把"公钥 + 主体身份信息（域名/组织）+ 有效期 + 扩展"绑定在一起，并由 CA 用其私钥对证书内容签名。最常用格式为 X.509，编码格式有 PEM（文本，----BEGIN CERTIFICATE----）与 DER（二进制），可含证书链。
　　2. PKI 与信任链。浏览器/系统内置了一批受信任的根 CA，形成"根 CA → 中间 CA → 终端证书"的信任链。验证证书时自顶向下校验签名与有效期，并检查域名匹配、吊销状态（通过证书吊销列表 CRL 或在线证书状态协议 OCSP）。若签名链断裂、过期、域名不匹配或吊销，即判定不可信并告警。
　　3. 证书的工程要点。HTTPS 证书需正确配置完整证书链；使用 Let's Encrypt 等自动化签发与管理工具（如 ACME 协议、certbot）；私钥权限最小化；及时续期并监控告警（证书过期是常见故障）。企业内部场景可用自建 CA 管理内部服务证书。
4. 密钥管理与密码资产治理。密码方案的安全上限取决于密钥的安全，密钥管理（Key Management）是工程落地中最容易失控的一环。核心要求包括：私钥与密钥必须使用专门的密钥存储（本地密钥库、KMS、硬件安全模块 HSM），绝不以明文方式随代码/仓库/镜像分发；遵循最小权限与职责分离（加密、解密、签名、审计角色区分），并控制可用密钥的人员范围；建立密钥的完整生命周期——生成、分装、使用、轮换（Rotation）、吊销与销毁，密钥一旦泄露立即吊销并全量回滚受其保护的数据；对密钥进行版本化与备份，避免"唯一密钥丢失导致数据永久不可读"；定期审计密钥使用记录（Audit Log）。此外，密钥与用于派生它的口令应分开存放，避免"拿到配置即拿到密钥"的一击即溃。良好实践是把云上 KMS/HSM 与本地加密框架（如 Kubernetes Secret 加密、数据库 TDE 透明数据加密）结合，统一管理各类密钥。
七、TLS 握手：现代安全传输的实践
　　TLS（传输层安全协议，Transport Layer Security，前身 SSL）是为 HTTP 提供机密性、完整性与认证的标准协议，HTTPS = HTTP + TLS。理解 TLS 握手有助于排查各类连接/证书问题。
　　1. 握手阶段。客户端与服务器协商协议版本（TLS 1.2/1.3）与密码套件（Cipher Suite，如 TLS_AES_256_GCM_SHA384）；服务器出示数字证书（含公钥）；客户端验证证书信任链与身份；随后双方通过密钥交换（如 ECDHE）在不泄露的情况下协商出共享的会话密钥；最后交换完成消息。TLS 1.3 优化了往返次数（更少 RTT，握手下行），并废弃了不安全的旧密码套件。
　　2. 安全属性。TLS 提供数据的机密性（会话数据用对称密钥加密）、完整性（经 AEAD 认证）与服务器（可选客户端）身份认证（通过证书）。正是因为证书验证，"中间人"才无法伪造成服务器。
　　3. 注意事项。应禁用过时的 SSL/TLS 1.0/1.1；证书私钥不得泄露；使用强密码套件（完整前向保密 ECDHE）；对合法 CA 欺骗保持警惕。对于非 HTTP 的应用（如数据库、消息队列、RPC），同样应启用 TLS/证书进行加密传输。ETL. 现代实践还包含 mTLS（双向 TLS，客户端也出示证书），用于服务间零信任访问。
八、量子密码学展望
　　量子计算的发展对现有密码体系带来深远影响，主要分为"威胁"与"机遇"两个方向。
　　1. 量子威胁：Shor 算法可在多项式时间内求解大整数分解与离散对数，因此 RSA、ECC、DH 等依赖这些难题的公钥密码在未来可扩展量子计算机面前将被"一击即溃"；Grover 算法会以平方根加速暴力搜索，削弱对称密钥与哈希的有效强度（例如使 128 位对称密钥的实际强度降为约 64 位），但可通过增大密钥长度（如用 AES-256/384）来对冲。
　　2. 后量子密码（PQC, Post-Quantum Cryptography）。NIST 已选出以格基密码（Lattice-based）为代表的后量子算法（如 CRYSTALS-Kyber 用于密钥封装、CRYSTALS-Dilithium 用于签名），其目标是即便量子计算机成熟仍保持安全。企业和标准化组织正推进"先收先存再解密（Harvest Now, Decrypt Later）"风险的应对与算法迁移（Crypto-Agility，可替换性）。
　　3. 量子密码学（QKD，量子密钥分发）。利用量子力学原理（如不可克隆定理、测不准原理）协商密钥，理论上可察觉任何窃听，实现"信息论安全"的密钥分发。QKD 需要专用量子信道与中继，成本高、距离受限，目前主要用于特定高安全场景的长远储备。
　　4. 工程建议。保持算法可替换性，避免把长期机密固化到某一算法；对超长期数据（如多年有效的加密内容）尽快评估哈希/密钥强度，并为后量子迁移预留接口。
九、从检索增强（RAG）角度看密码学
　　把密码学做成可检索的知识语料，同样需要讲求检索区分度。
　　1. 按"算法类别+用途"分维。可用"对称/非对称/哈希/签名/证书/TLS/量子"作为一级维度，用"加密用途/密钥长度/推荐度/禁用项"作为标签，让用户能精确检索"HTTPS 用什么加密""口令该用什么哈希""RSA 还安全吗"。
　　2. 强调"推荐 vs 禁用"。密码学检索最怕答案含糊。语料应明确给出推荐（AES-256-GCM、SHA-256、Argon2、ECDHE、X25519、Ed25519）与禁用（DES、MD5、SHA-1、RC4、ECB、SSL 旧版本），并说明原因，使问答系统能给出可执行的选型建议。
　　3. 关键参数与别名互注。记录与算法绑定的密钥长度、IV/Nonce 规则、密码套件名称、证书格式（PEM/DER/X.509）、协议缩写全称（TLS/SSH/JWT/OIDC），提升精确命中。
　　4. 结合安全开发。补充"令牌/口令存储规范、证书生命周期（签发/续期/吊销）、TLS 配置基线"等工程清单，让语料不仅解释原理，也能支撑具体开发与排错决策。
　　5. 关联真实场景。把密码学概念映射到用户常见场景建立检索锚点，例如"HTTPS 为什么安全""登录口令怎么存""签名与加密有何区别""如何校验文件完整性""量子会威胁现有加密吗"，让问答系统能基于场景触发对算法与流程的准确回答，提升命中质量与可解释性。
十、总结
　　密码学以机密性、完整性、认证与不可抵赖为目标，通过对称加密（AES 及其 AEAD 模式）保证高效保密、通过非对称加密（RSA 衰老而 ECC 崛起）支撑密钥交换与数字签名、通过哈希与加盐慢哈希守护口令与完整性、通过证书与 PKI 建立可信身份链、通过 TLS 握手落地 HTTPS 等安全传输，并面对量子时代进行后量子算法的迁移布局。正确的密码学实践来自"用成熟标准算法、管好密钥、遵循认证完整性措配、保持算法可替换性"。掌握这些，才能构建真正经得起考验的安全系统。
